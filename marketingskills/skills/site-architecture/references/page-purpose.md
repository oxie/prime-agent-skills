# Page purpose and content recipes

Use with site-architecture for the page's job and content requirements, not a
fixed site template. Read only the relevant recipe. Existing brief, content,
architecture and permissions win. This reference does not authorize research,
publishing, deleting pages or adding a CMS, search service or data collection.

## Choose by the visitor's task

Start from the supplied audience, real content inventory and main visitor task.
For a new or substantially redesigned page, briefly connect: visitor task →
content needed → useful next action → deliberately omitted features. Fit this
into the existing plan; do not create another document or approval round.
If the brief already settles a choice, reuse it. Do not make every website a
sales funnel. Personal writing, public information and documentation can succeed
without a signup CTA, lead capture or product pitch.

For hierarchy use [site-type templates](site-type-templates.md). For visual
composition and component choice use Hallmark, which owns layout and styling.
Copywriting owns marketing prose; content-strategy owns editorial planning;
schema and seo-audit own current structured-data and search checks. No mandatory
second pass: consult another owner only for a relevant unresolved question.

## Blog index and article are different pages

**Index: help readers choose what to read.** Surface titles, honest excerpts,
useful dates/authors and topics when they help selection. A chronological list
fits a small personal journal; an editorial publication may need featured work,
topic sections and archives. Add categories, search or filters only when the
content volume and reader tasks justify them. Provide navigable archive pages
when material continues beyond the initial list; do not strand it behind a
nonfunctional load-more control.

**Article: help readers understand one piece.** Match the template to an essay,
news report, tutorial or product update. Use a clear title, actual author and
meaningful publication/update information. Support a readable body, contextual
links and relevant media. For a long navigable guide, a TOC can help; a short
personal essay needs no forced TL;DR, sales CTA, featured image or share toolbar.
Related reading should be genuinely related, not a quota. Show substantive
update dates honestly; do not hide original publication solely to imply freshness.

No minimum word count, keyword density, link quota or guaranteed SEO benefit.
A page-template request does not automatically require competitor research.

## Portfolio, showcase and case study

**Portfolio: help someone assess this person's work and fit.** Select real
projects with names, role/contribution, context and links to deeper work where
available. Order by relevance to the intended audience, not equal card quotas.
Use authentic work as the main evidence; biography, services or contact support
that purpose. Three projects rarely need filtering. A writer's portfolio may be
a title-led list; a photographer's may be image-led. This portfolio recipe is
local synthesis, not an upstream dedicated portfolio skill.

**Showcase: help visitors discover work made by a community or product's users.**
Useful item fields include title, creator credit, preview and destination. Respect
permission and attribution. Categories help only when there is useful variety.
A submission CTA needs an actual approved submission process; do not invent one.

**Case study: explain a particular project or outcome.** Connect the challenge,
constraints, personal/team role, decisions, delivered work and supported results.
Use real artifacts and tradeoffs, not just a gallery. Quantitative outcomes and
client quotations are optional evidence, never fill-in requirements. If outcomes
were not measured, describe what was delivered and what remains unknown. Do not
invent customers, logos, testimonials, screenshots or before/after metrics.

## Services

Help visitors determine fit, scope and how to engage. Explain who the service is
for, what is included/excluded, how the work proceeds and available proof. Use a
compact overview for a few services; a hub plus detail pages when materially
different offerings need explanation. A quote, booking or contact action must
match an actual process. Pricing or packages appear only when supplied/approved;
a consulting page need not imitate a subscription pricing table.

## Documentation and resource hubs

**Documentation: help users complete a task or answer a precise question.**
Separate first-success/quick start, how-to guides, concepts, reference and
troubleshooting as the material requires. A tiny tool can use one well-structured
page; large docs may need hierarchical navigation, search and version context.
Keep examples consistent with the actual API/product and show meaningful errors
and prerequisites. An API reference may have its own pages or live in a larger
docs site; neither structure is universally required. Access control, not robots
rules, protects private documentation.

**Resource hub: help people find a useful asset across formats/topics.** Identify
real resource types and useful metadata: title, format, subject, intended audience
and destination. Feature only meaningful selections. Filters/search need enough
content and a working implementation; a handful of resources can be simple links.
Distinguish reading/downloading from submitting personal data. Do not gate public
resources or add a newsletter collection flow unless it serves the approved brief.

## Handoff and useful omissions

In the existing plan or delivery, identify the chosen page purpose, essential
content and any material missing inputs. Explain consequential omissions briefly:
for example, no filters for three projects, no invented case metrics, or no sales
CTA on a reference page. Missing evidence is not permission to manufacture it.
Do not report a structure as verified design or a conversion improvement.

Hallmark and the project's existing tests/browser workflow verify implemented
layout and interactions. This reference neither launches tools nor certifies the
rendered result. It supplies content decisions, not a mandatory feature checklist.
