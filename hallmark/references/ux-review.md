# Task-centered UX review and contextual delight

Use this reference only for a requested usability review or an in-scope interaction
improvement. Keep the selected Hallmark workflow: an audit is strictly read-only.
Do not run a build, start a server, inject a detector, edit files or save review logs
without separate authorization. A chat report is enough. No score, mandatory
interview, worker, product document or new design authority is required.

## Follow one real task

Reuse the brief, current product facts and design system from their existing owners.
Do not create or migrate PRODUCT.md or DESIGN.md. If useful, name the surface's
purpose: decide, operate, read or experience. A dense operating screen can favor
familiar controls and fast comparison; a reading surface need not become a campaign.

Walk from the user's starting information through the decision to the result. At
each step, ask what the person knows, must remember, can do and can recover. Choose
only relevant lenses; these are reasoning aids, not recruited users or user-test data:

- **Novice:** can someone find the first action and understand task-specific terms?
  Use existing contextual help where it answers the question at the point of need.
- **Expert:** preserve scanning, useful density and learned shortcuts. Count real
  decisions and unnecessary steps, not options alone. More than four valid choices
  is not a defect; hiding them can make comparison harder.
- **Distracted or returning:** after interruption, are location, selected item,
  entered work and next action still clear? Check cross-screen memory bridges.
- **Touch or relevant access needs:** can the task be understood without hover,
  precision gestures or assumed sensory cues? Use [app-quality.md](app-quality.md)
  for control, state, reflow and accessibility checks; do not duplicate or score them.

## Find task friction, not aesthetic violations

- **Memory and context:** trace a value from where it is learned to where it is
  needed. If a return trip loses it, name the exact value, screens and decision.
  Propose a nearby summary or retained selection using authorized data, not a new
  data source. Do not expose restricted information to avoid a memory burden.
- **Prevention and control:** for a consequential action, is its target and effect
  clear before commitment? Check existing cancel/back/undo contracts. Propose only
  safeguards suited to the risk; do not invent autosave, undo or backend support.
- **Recovery:** distinguish rejection, pending work, partial completion and unknown
  outcome. Identify what is preserved and which next action really exists. A retry
  may duplicate a payment or submission; do not recommend it without that contract.
- **Help:** does existing guidance answer this task's question in its vocabulary
  without losing context? A short explanation beside the relevant control may beat
  a tour. Do not require documentation, onboarding or jargon removal everywhere.

Prioritize blocked tasks, costly errors and lost work before optional polish. Keep
intentional eyebrows, neutral gray, familiar layouts and a no-motion brief unless
specific evidence establishes a problem. Taste is not a functional failure.

## Make the emotional response useful

Choose no flourish when certainty is enough. If a moment warrants personality,
state the intended feeling and why it fits this product's stakes and voice:

| Moment | Smallest useful response |
|---|---|
| Routine save | Clear, truthful confirmation; no repeated celebration |
| Meaningful completion | Acknowledge real effort without delaying the next task |
| Waiting | Explain the actual pending operation; no invented percentage or delay |
| First use | Make the available next action clear before adding character |
| Failure or recovery | Explain the problem and safe next step first; no jokes about loss, money or privacy |
| Discovery or mastery | Reveal real utility without hiding required functionality |

Consider repetition and interruption: does the response still help on the hundredth
use? Motion, sound and haptics are optional, not the definition of delight. Preserve
a clear static path; sound needs consent and must respect mute. Do not add assets,
dependencies, factual claims or capability merely to embellish a moment. Requested
cinematic direction or canvas effects remain separate optional specialists.

## Report what the evidence supports

For each useful finding, name **task/step, evidence, impact, smallest recommendation
and untested check**. Label source observations, supplied traces, observed behavior
and inference separately. Static source cannot establish a user's difficulty,
rendered contrast or a working recovery path. Simulated lenses establish hypotheses,
not measured usability, accessibility compliance or conversion gains.

If a separately authorized detector is available, form the first design judgment
before reading its findings. Then reconcile: corroborated defect, plausible concern
needing a check, or valid counterexample. Do not run a detector by default, accept
its taste rules as authority, or rerun an unchanged scan just to produce agreement.
Report important preserved choices as well as defects; no health score is needed.
